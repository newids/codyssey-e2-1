# Judge Review — 심사 검증 루브릭

## 검증의 태도

통과시킬 이유가 아니라 **떨어뜨릴 이유**를 찾는다. 지적은 "예상 심사 질문" 형태로 쓴다 — 팀이 방어를 준비할 수 있는 지적만 가치가 있다.

## 루브릭 1 — 과제 목표 대응 (Mission-e2-1 §3)

산출물만 읽고 아래 6개 질문에 답할 수 있어야 한다. 답할 수 없으면 반려:

1. 도메인(AI Fintech)의 산업 현황과 주요 이슈가 파악되는가?
2. AI가 해결할 문제의 정의와 배경이 서술되는가?
3. 타겟 사용자와 니즈가 구체적인가 (세그먼트 기준이 논리적인가)?
4. 적용 AI 기술의 종류와 **선택 이유**가 설명되는가?
5. 팀 역할 분담이 명시되고 전원 기여가 드러나는가?
6. 기대 효과와 향후 발전 방향이 서술되는가?

## 루브릭 2 — 심사 공격 질문

각 산출물에 대해 최소 다음을 공격한다:

- **차별화**: "기존 금융교육 앱/은행 예방 서비스와 뭐가 다른가?" — 한 문장으로 답이 나오는가
- **AI 필연성**: "이거 AI 없이 규칙 기반으로 되지 않나?" — 기능별로 방어되는가
- **도메인 적합성**: "이건 에듀테크지 핀테크가 아니지 않나?" — 금융 도메인 방어 논리가 있는가
- **현실성**: "이 팀이 이걸 어떻게 증명하나?" — 근거 없는 실행력 주장이 없는가
- **수익/지속성**: "누가 왜 돈을 내는가?" — 유인책과 지불 주체가 특정되는가
- **중복 서비스**: "은행/기관이 이미 하고 있지 않나?" — 기존 서비스 조사가 반영됐는가

## 루브릭 3 — 형식 게이트 (기계적 검사)

- [ ] 발표자료 10쪽 이내, 팀 역할 분담 슬라이드 존재
- [ ] 모든 통계에 기준 연도·출처 병기
- [ ] 수식(LaTeX) 표기 없음
- [ ] `[TODO]` 플레이스홀더 잔존 여부 (제출 직전 검증 시 반려 사유)

## 정합성 교차 검사 (경계면 검증)

존재 확인이 아니라 **동시에 열어 대조**한다:

| 검사 | 방법 |
|---|---|
| 수치 일치 | 같은 통계가 기획서·덱·브리프에서 같은 수치+같은 출처 표기인지 grep으로 대조 |
| 용어 일치 | 서비스명·기능명·세그먼트명이 문서마다 동일한지 |
| 다이어그램-기술표 대응 | 아키텍처의 컴포넌트가 AI 기술 표의 행과 1:1 대응하는지 |
| 전략-산출물 추적 | 전략 개정안의 "버린 것"이 기획서·덱에 잔존하지 않는지 |

## 판정 출력 형식

- **판정**: 통과 / 반려 (반려 사유 심각도: 반려 / 수정 권고 / 참고)
- 각 지적: 위치(파일 §섹션) + 예상 심사 질문 + 수정 요구 + 담당 에이전트
- 재검 시: 이전 반려 사유의 해소 여부를 먼저 확인(회귀 검사)하고 새 지적과 구분한다
